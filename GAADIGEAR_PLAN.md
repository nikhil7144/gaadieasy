# GaadiGear Architecture Plan

## Goal
Add GaadiGear — a multi-seller accessories/parts/riding-gear marketplace — inside Gaadieasy.com, scoped to vehicles via a compatibility system (vehicle type → brand → model → variant), cross-sold on vehicle pages via a "Recommended Gear" widget. Read-heavy, write-light: buyer-facing reads must never live-join across products/compatibility/categories, mirroring the `vehicle_pricing_cache` philosophy (see `PRICING_CACHE_PLAN.md`).

A full architecture spec (schema, taxonomy, APIs, flows, refunds/payouts, GST pricing) was provided by the user and reconciled against the actual codebase/live database — several of the spec's assumptions didn't hold and were corrected here.

---

## Key architecture decisions

### 1. Vehicle type mapping (resolved via live DB inspection, not assumption)
Live `vehicle_categories` (7 rows, 115 `vehicle_models` at the time this was built) map to 4 new `vehicle_types`:

| category slug | → `vehicle_type` |
|---|---|
| `cars` | Car |
| `bikes`, `scooters` | Two Wheeler |
| `commercial-vehicles`, `ev-commercial-vehicles` | Commercial Vehicle |
| `passenger-ev-vehicles` (0 models — reserved) | Three Wheeler |
| `ev-vehicles` (orphaned, 0 models) | excluded, marked inactive |

Mapping lives on `vehicle_categories.vehicle_type_id` (category level, not per-model) because EV-ness for cars/bikes/scooters is already expressed via `vehicle_variants.fuel_type`, not a separate category. `segment` reuses `vehicle_models.body_type` directly — no new column.

### 2. Cache refresh — application-level, not cron/trigger
Mirrors `vehicle_pricing_cache` exactly: no pg_cron, no DB trigger, no Edge Function. `lib/services/gear-catalog-cache/index.ts` upserts `gear_catalog_index`/`gear_model_cache` rows from plain service functions, called **awaited** (not fire-and-forget like the pricing cache) from every product mutation — deliberate deviation, since this is Vercel serverless and un-awaited background work isn't guaranteed to finish. A manual "Rebuild now" admin button (`/admin/gaadigear/products`) handles full backfills and the rare broad-compatibility case (see below).

**Narrow vs. broad compatibility fan-out:** `invalidateModelCacheForProduct` recomputes affected `gear_model_cache` rows synchronously only for narrow compatibility (`model`, `variant`, `brand` — bounded, typically 1-20 models). Broad compatibility (`vehicle_type`, `segment`, `global`) is deferred to the manual rebuild rather than blocking the request — could touch all 115 models at once.

### 3. Seller account model — mirrors dealer's table shape, new self-signup
`sellers` (business entity) + `seller_users` (join table, `role: seller_owner | seller_staff`, real `auth.users` rows) — same shape as `dealers`/`dealer_businesses`/`dealer_users`, but **with** a tracked migration (dealer's version has none) and **with** public self-signup (dealers have none — only admin-created logins). Context resolution: `getSellerAccessContext()` in `lib/services/seller-auth/index.ts`, mirroring `getDealerAccessContext()`. No RLS — consistent with the rest of the codebase (app-level guards only).

### 4. Admin UI — dense list-first, intentionally diverges from existing `/admin`
GaadiGear admin screens (`/admin/gaadigear/*`) use hairline dividers, colored-dot status, inline text-link actions, plain filter row — not the existing card-grid/split-panel Manager pattern. Confirmed with user as a deliberate visual fork, not an oversight.

### 5. Buyer identity & cart (decided 2026-07-07, for Phase 5)
- Buyers get an **optional account** — guest checkout works; a logged-in buyer additionally gets order history. Buyer auth is plain Supabase Auth (no role, no business entity, no join table — much lighter than seller/dealer).
- Cart is a **persisted table** (user's explicit choice, overriding the simpler client-side-only recommendation), keyed by `cart_token` (httpOnly cookie) so it works for guests too:
  - `gear_carts`: `id`, `buyer_id` (nullable), `cart_token` (unique), timestamps.
  - `gear_cart_items`: `id`, `cart_id`, `product_id`, `variant_id`, `qty`, unique on `(cart_id, product_id, variant_id)`.
  - Merge-on-login: a guest cart's `buyer_id` gets backfilled (or merged into an existing account cart) when they sign up/log in.
- Not yet migrated — schema addition beyond the spec's original design, to be added when Phase 5 starts.

### 6. Payment gateway — open, not blocking
No gateway integrated anywhere (confirmed: greenfield). Razorpay recommended (Route product matches the per-seller payout model) but not decided. Needed before Phase 5 starts.

### 7. Table naming
`gear_` prefix added to catalog-side tables not already prefixed in the spec, to avoid ambiguity with existing generic-sounding tables (`vehicle_categories`, `brands`): `categories`→`gear_categories`, `products`→`gear_products`, `product_compatibility`→`gear_product_compatibility`, `product_variants`→`gear_product_variants`, `accessory_brands`→`gear_brands`, `model_gear_cache`→`gear_model_cache`. Seller/order/refund tables keep the spec's original names.

### 8. Compatibility model — strict vehicle-type-first drill-down (corrected mid-build)
Compatibility is **never** a flat "pick one of six types" list. Vehicle type is always mandatory first. "Universal" only ever means "select all at this level, not skip the level" — all brands under a vehicle type (`compatibility_type='vehicle_type'`), all models under a brand (`'brand'`), all variants under a model (`'model'`), or specific variants (`'variant'`). The schema's true cross-vehicle-type `'global'` type still exists (a real product — "Riding Jacket" — got mistagged this way by an earlier, worse picker UX) but is **no longer creatable from the seller UI**; sellers can only reach it by direct DB access. Every non-global compatibility row also stores `vehicle_type_id` (even brand/model/variant rows, where it's not needed for matching) purely so an existing product's compatibility can be reconstructed reliably when reopened for editing.

### ✅ Removed admin moderation gate — auto-publish on completeness (2026-07-08)
User feedback: editing a live product forcing it back to `pending_review` every time — even with no meaningful change — was unwanted, and the ask was to auto-approve products instead of requiring manual admin review. Since every field except photos is already mandatory at creation time (title, category, mrp, selling price, compatibility — all enforced by the zod schema on `POST`), "is this product complete enough to go live" reduces to one check: does it have at least one photo.

- `updateProductForSeller` no longer force-flips a live product back to `pending_review` on edit — it just stays live.
- `submitProductForReview` renamed to `publishProduct`: validates `images.length > 0` and sets status directly to `live` (was `pending_review`) — no admin action in the loop. ### ✅ Fixed the recurring "Unexpected token 'I' ... is not valid JSON" error across every file-upload route (2026-07-09)
